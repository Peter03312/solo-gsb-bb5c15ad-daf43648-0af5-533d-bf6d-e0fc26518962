# 舞台换景顺序优化

一个舞台演出换景顺序优化 Web 应用：录入不超过 **12 个场景**及其道具集合，设置**前后依赖**、**固定序位**、**禁止相邻**三类约束与可选的**单段道具操作上限**，系统自动计算满足全部约束且**道具增减次数最少**的演出顺序，并展示每次换景的道具增减明细与各段上限用量。无解时会指出一组可复现的冲突约束；仅因单段上限导致无解时会给出"放宽到几件即可有解"的明确提示。支持保存方案并随时重新载入编辑。

**巡演装箱**：全部场景道具自动汇总去重（保持录入顺序）生成待运输清单，逐件设置正整数重量，填写**单箱承重**与**不能同箱的互斥道具对**，服务端在不超过 **14 件**道具内求**箱数最少**的完整分箱——每箱总重量不超限、不含互斥对，箱内与箱间均按道具录入顺序稳定展示。单件超重、道具超过 14 件或配置无效时给出具体提示；结果列出每箱道具、重量与总箱数。装箱配置随方案一起保存与载入。

**巡演备货**：以当前场景道具全集（与场景录入、装箱同一汇总口径）为需求清单，在页面上**勾选已备齐的道具**，未勾选项即为**缺件**（至多 **14 种**）；再录入至多 **30 个采购包**（包名、**正整数价格**、所含道具，每包至多购买一次），包内道具必须来自需求清单，但**允许重复覆盖缺件、允许只含已备齐道具**。服务端用覆盖集 DP 求**覆盖全部缺件的最低总价组合**；总价相同时**优先购买包数少**，仍相同时**按采购包录入顺序稳定选取**（尽量选用录入更早的包）。页面展示缺件清单、所选采购包（录入顺序、价格、覆盖的缺件）与最低总价；**场景道具、备齐标记或任何采购包报价改变后，旧结果立即清除**，需要重新计算。没有缺件时返回空组合、总价 0；缺件超过 14 种、采购包超过 30 个、包名为空或重复、价格非正整数、包内出现需求清单之外的道具或缺件无法被任何包覆盖时，明确报错且不输出采购方案。备货标记与采购包随方案一起保存与载入。

一次求解还可请求**最多 3 条顺序不同的备选节目单**：经典模式按道具操作总数升序排列；时长受限模式先按入选可选场景价值降序、再按操作总数升序排列；完全同分时按场景录入顺序稳定排序。每条备选都逐条满足依赖、固定序位、禁止相邻、时长与单段操作上限（求解器在每个 DP 状态上保留至多 K 条不同路径，不会因某个中间状态只留一条最优路径而漏掉后续候选）。页面并列展示各方案的取舍、入选 / 舍弃场景、换景明细与指标，选中任一条即可按该顺序进入现有「演出中重排」流程。

支持两种编排模式：

- **经典编排**：全部场景必须参演，仅最小化道具增减次数。
- **时长受限编排**：为每个场景设置**时长**、**必演**标记与**可选场景价值**，并指定**整场时长上限**。求解器从场景中选择一个包含全部必演项的子集参演（未入选场景不参与任何约束，固定序位按入选后的演出序列计算），**先最大化入选可选场景的价值总和，再最小化道具增减次数**，并展示入选 / 舍弃场景、已用 / 剩余时长与换景明细。必演场景已超时或不存在可行编排时给出对应无解提示。

**单段道具操作上限（可选）**：在场景表上方勾选后填写件数 N，表示**开场布置**以及**从上一舞台状态切到下一场景的每次换景**中，"撤下道具数 + 上台道具数"合计**最多 N 件**。求解器把开场布置与每次换景都作为受限边，在同时满足既有约束与该上限的候选编排里，仍按"经典最小化增减次数 / 时长受限先价值后增减"的原目标选全局最优顺序；上限过低导致无解时，会二分算出"放宽到 N′ 件即恢复有解"并明确提示。不勾选则不限制。

**演出中重排（replan）**：演出开始后情况有变（实际道具与计划不同、想舍弃某些未演场景），可在任意一次求解结果上**确认已完成的连续前缀**并**录入当前舞台实际道具**，系统只重排剩余场景：

- 已完成顺序不可改变，只能继续向后确认前缀；跨前缀的依赖按**完成事实**校验（已演完的场景事实上先于一切未演场景；若某场景已演完而它的前置还没演，明确指出这一不可补救的冲突）；
- **固定序位仍按整场绝对位次**计算（如被固定到第 3 位的场景实际在第 2 位演完，或该位次已被已完成场景占住，均会指出具体冲突）；前缀内部的禁止相邻同样逐条检查；
- 时长受限模式自动**扣除前缀已用时长**，**已完成可选场景的价值计入结果**，剩余选择继续按"价值优先 → 换景次数次优"；
- **首个剩余场景的代价（以及单段上限的约束与用量）从当前实际道具计算**（可包含计划外道具），而非原计划的末场景；已完成前缀的各段不再受上限限制，前缀保持不变；
- 结果**并列显示原计划与"前缀 + 新后缀"**、后缀代价与整场代价的增减、价值变动，以及被舍弃 / 新增入选的场景；
- 保存方案时连同重排进度与单段上限一起持久化，重新载入后自动恢复，可**在此基础上继续重排**。

**换景人员排班**：在当前求解、采用备选或演出中重排得到的节目单之后，可录入 **2～4 名工作人员**与**每件道具单次搬运所需的正整数分钟**，服务端只对**待执行的开场与换景步骤**排班：每段必须先完成全部**撤下**才能开始**摆上**，同一人一次只处理一件道具、不同人可并行。每个阶段（撤下 / 摆上）最多 **14 项任务**，系统用精确算法求**最短完工时间**并给出**可执行且稳定**（同输入结果恒定、按道具与人员顺序确定映射）的人员分工，汇总**各段耗时与全场搬运总耗时**。工作人员数量 / 姓名不合法、某阶段超过 14 项任务、或有道具缺少正整数工时，都会就地逐条明确提示，不产生排班结果；页面按"撤下 / 摆上"两阶段展示每人的任务链与时间轴，**节目单或工时一旦改变，旧排班自动作废**。

## 快速开始（单条命令）

```bash
docker compose up --build
```

启动后访问：**http://localhost:3000**

> 依赖安装与数据目录初始化均随容器启动自动完成，无需额外步骤。
> 若使用旧版 Compose 插件，命令为 `docker-compose up --build`。

停止：`Ctrl+C` 或 `docker compose down`。保存的方案存放在名为 `plans-data` 的卷中，重启不丢失。

## 本地开发（不用 Docker）

```bash
npm install
npm start          # 访问 http://localhost:3000
npm test           # 运行求解器 + 装箱 + 排班单元测试
npm run fuzz       # 时长受限模式随机对拍
npm run fuzz:replan # 演出中重排随机对拍
npm run fuzz:alt   # 备选节目单（k-best）随机对拍
npm run fuzz:pack  # 巡演装箱随机对拍
npm run fuzz:stock # 巡演备货随机对拍（枚举全部包子集验证最低价与稳定选择）
npm run fuzz:schedule # 换景排班随机对拍（穷举验证最短工时）
```

要求 Node.js ≥ 18。方案数据默认保存在 `./data/plans.json`（可用环境变量 `DATA_DIR` 修改）。

## 功能说明

- **两种模式**：页面顶部可切换「经典编排」与「时长受限编排」。
- **场景与道具**：最多 12 个场景，每个场景一组道具（逗号分隔录入）。
- **单段道具操作上限（可选，两种模式通用）**：在场景表上方勾选"限制单段道具操作上限"并填写正整数 N。开场布置与每次换景的撤下 + 上台合计均不得超过 N 件；不勾选则不限。结果区每个步骤都标注"本段 用量/N 件"（达到上限高亮），总计行给出最大单段用量。上限导致无解时提示放宽到最小可行件数。
- **时长受限编排附加字段**：
  - 时长 `duration`：非负整数（分钟）；
  - 必演 `required`：勾选后该场景必须入选（必演场景不参与可选价值统计）；
  - 可选价值 `value`：该场景入选时贡献的价值，仅对非必演场景生效；
  - 整场时长上限 `timeLimit`：入选场景总时长不得超过它。
- **约束**（未入选场景不参与约束；固定序位按入选后的演出序列计算）：
  - 前后依赖：场景 A 必须排在场景 B 之前；
  - 固定序位：某场景必须排在第 N 位；
  - 禁止相邻：两个场景不得紧挨着演出。
- **优化目标**：
  - 经典模式：在满足约束与单段上限的候选中，`开场布置道具数 + 各次换景（撤下数 + 上台数）之和` 最小。
  - 时长受限模式：① 入选可选场景价值总和最大 → ② 道具增减次数最少（均须满足单段上限）→ ③ 同分保持确定顺序。
- **备选节目单（最多 3 条）**：在求解区的「备选节目单」下拉中选择 2 或 3（默认「仅最优 1 条」，与原行为完全一致）。求解后：
  - 主结果区展示**方案 1（最优方案，即当前节目单）**，其下依次列出方案 2、3 的顺序、指标与取舍——经典模式给出相对方案 1「多几件次操作」，时长受限模式给出「少多少可选价值 / 多几件次操作」，并标出相对方案 1 的入选 / 舍弃场景差异；
  - 每条方案都可展开查看完整换景明细与每段用量；经典模式按**道具操作总数升序**，时长受限模式按**价值降序 → 操作总数升序**，完全同分时按**场景录入顺序**稳定排序，顺序两两不同；
  - 点击某条备选的「✓ 采用此方案进入演出」即把该顺序替换为当前节目单，随后可在「🎬 演出中重排」面板按该顺序确认已完成前缀继续演出（保存 / 重排等既有行为不变）；
  - 若满足全部约束的编排本身不足所请求的条数，则返回实际存在的条数；无可行编排时仍返回原有的无解分析。
- **结果展示**：演出顺序、道具增减总次数、最大单段用量与每次换景的撤下 / 上台明细及"本段 用量/上限"标注；时长受限模式额外展示入选 / 舍弃场景清单、已用与剩余时长、入选价值。
- **无解分析**：
  - 经典模式：若仅因单段上限无解，返回 `prop-limit-infeasible` 并给出放宽到几件即可有解；否则优先报告依赖环；其余情况给出一组极小冲突约束核心（去掉其中任意一条即恢复有解）。
  - 时长受限模式：必演场景总时长超限单独提示；仅因单段上限无解时给出最小可行上限；必演项间的依赖环 / 固定序位等"结构性"冲突给出极小核心；若结构上可行但时长上限不足以插入缓冲场景，给出提高上限 / 放宽约束的建议。
- **演出中重排**：
  - 在结果区的「🎬 演出中重排」面板选择"已完成到第 N 位"（只能在当前已确认前缀之后继续延长），并用逗号录入当前舞台上的实际道具（可点「取第 K 个场景的计划道具」快速带入末场计划道具后再修改）；
  - 点击「只重排剩余场景」后，页面并列展示原计划与新的"前缀 + 后缀"：已完成部分标 ✅、明细划线置灰，待执行部分单独标记，首个后缀场景显示"从当前舞台实际道具"的撤下 / 上台；设置了单段上限时，上限只作用于后缀各段（含首段），每段同样标注用量；
  - 时长受限模式显示前缀已用时长 / 后缀可用时长、前缀已实现价值、价值与整场代价的增减；
  - 前缀冲突（依赖顺序、跨前缀依赖、固定序位错位 / 位次被占、前缀内禁止相邻、前缀已超时）会就地列出每一条具体冲突，不进行重排；
  - 重排结果即新的当前节目单，可反复继续重排；保存方案后下次载入自动恢复到该进度。
- **巡演装箱**：
  - 待运输道具由全部场景道具**汇总去重**自动生成（保持场景序与场景内录入顺序），场景道具编辑后清单实时同步；也可点「↻ 同步道具清单」手动刷新；
  - 逐件设置**正整数重量**（新道具默认 1，可直接修改），填写**单箱承重**（正整数），并可添加任意条**不能同箱的互斥道具对**（重复对自动去重，删除道具时相关配置自动清理）；
  - 点击「📦 计算装箱方案」后由服务端求**箱数最少**的完整分箱：每箱总重量不超过承重、不含互斥对；结果列出**总箱数、道具总重量**，以及每箱的道具清单（带单件重量）、件数、箱重量与满载 / 剩余空间；箱内道具与箱间顺序均按道具录入顺序稳定展示，重复求解结果一致；
  - **单件超重**（重量 > 承重，表格中该道具会同步标红）、**道具超过 14 件**、承重 / 重量非正整数、互斥对引用不存在的道具等配置问题都会给出具体提示，不产生结果；
  - 装箱配置（承重、逐件重量、互斥对）随方案一起保存与载入，旧方案按默认配置（承重 10、重量 1）处理。
- **巡演备货**：
  - 需求清单由全部场景道具**汇总去重**自动生成（与装箱同一口径，保持场景序与场景内录入顺序），场景道具编辑后清单实时同步，也可点「↻ 同步需求清单」手动刷新；
  - 在需求清单上**勾选已备齐道具**，未勾选的即为**缺件**（缺件超过 **14 种**时按钮禁用并给出提示，无法计算）；
  - 录入至多 **30 个采购包**：包名不可为空或重复，价格为**正整数**，所含道具逗号分隔且必须来自需求清单（包内重复道具自动去重；含需求清单之外道具的包行会标红）；每包至多购买一次，包可重复覆盖缺件、也可只含已备齐道具；
  - 点击「🧮 计算最低总价组合」后由服务端求覆盖全部缺件的最低总价方案，结果列出**缺件清单、采购包数量、最低总价**，以及每个入选采购包的录入序号、价格、**覆盖到的缺件**与全部包含道具（入选包按录入顺序展示）；
  - 选择规则：**总价最低优先 → 购买包数最少 → 包下标集合字典序（录入更早的包优先）**，同输入重复计算结果恒定；
  - **没有缺件**时直接返回空组合、总价 0；**缺件超过 14 种、采购包超过 30 个、包名重复 / 为空、价格非正整数、包为空或含需求清单之外的道具、缺件无法被任何采购包覆盖**时，逐条给出具体提示，不产生采购方案；
  - **场景道具、备齐标记或采购包（名称 / 价格 / 道具）任一改变后，旧采购结果立即清除**，需要重新计算；备齐标记与采购包随方案一起保存与载入（旧方案按空白备货配置处理），保存的只有输入、不保存旧结果。
- **换景人员排班**（面板接在求解 / 采用备选 / 演出中重排后的当前节目单之后）：
  - 填写 **2～4 名工作人员**（姓名不可为空或重复，可随时增删）与**每件道具单次搬运的正整数分钟**（撤下 / 摆上同值）；道具清单由当前节目单的**待执行步骤**（开场布置、从舞台实况切入的首段及之后的每次换景；`phase:"done"` 的已完成前缀不参与）按段顺序、先撤下后摆上自动汇总去重，新道具自动出现在工时表中，已删道具的旧工时自动清除；
  - 点击「🗓 计算人员排班」后服务端求**最短完工时间**：每段撤下全部完成后摆上才开始，同一人一次一件、不同人并行；结果按段列出**撤下 / 摆上两阶段**每名人员的任务链（道具、工时、全场时间轴上的起止分钟）、各段耗时、全场搬运总耗时与各人累计搬运时间；
  - 同一输入结果**稳定一致**（箱内 / 箱间均按道具录入顺序映射到 1～N 号人员），重复请求结果相同；
  - **每阶段（撤下或摆上）最多 14 项任务**（撤下与摆上分别计数：开场布置只有摆上阶段，一次换景则各有一个阶段），任一阶段超限时按钮禁用并指出是第几段、哪个阶段、各有多少项；工作人员数量 / 姓名不合法、有道具缺少正整数工时（表格中标红、按钮禁用）、工时配置包含无关道具等情况都给出具体提示，不产生结果；
  - **节目单改变（重新求解、采用备选、继续重排、载入方案）或工时 / 人员修改时，旧排班立即清除**，需要重新计算。
- **方案管理**：保存、列表、载入重新编辑、删除；新字段（模式、时长上限、单段道具操作上限、场景时长 / 必演 / 价值、重排进度、装箱配置）随方案一起持久化，旧方案仍可正常载入（按经典模式、不限单段上限、默认装箱配置处理）。

## 算法

场景数 n ≤ 12，均为子集动态规划（Held-Karp 风格），复杂度 `O(2^n · n²)`（12 个场景约 70 万状态），求解在毫秒级完成，结果保证全局最优且确定（同代价取下标字典序）。请求备选节目单时为同结构的 k-best DP，每状态保留至多 3 条路径，n=12 时仍在数百毫秒内。

- **经典模式**：状态 `(已排场景集合, 末尾场景)`，转移时校验前置依赖、固定序位与禁止相邻，代价为相邻场景道具集合的对称差大小。单段上限作为受限边：开场状态只接纳布置件数 ≤ 上限的场景，转移只走过对称差 ≤ 上限的边。
- **时长受限模式**：单个全局子集 DP 同时求出**每个**入选子集的最优排列——利用"末尾场景在集合内无后继、其固定序位恰为集合长度 − 1"这一归纳刻画，使涉及未入选场景的约束自然失效；最后在含全部必演项且不超时的子集中按"价值最高 → 代价最低 → 掩码升序"择优。单段上限同样过滤开场与换景边（空节目单无任何边，恒可行）。无解归因另用一次"必演必排、可选可作缓冲、不限时长、不限单段"的结构可行性 DP 判断冲突是否可经提高上限解除。
- **上限无解诊断**：受限 DP 无解时再跑一次"去掉单段上限"的 DP：若该次有解，说明只是上限过低，在 `[0, 最大单段代价]` 上对可行性做二分（可行性关于上限单调），求出恢复有解所需的**最小单段上限**随提示返回；否则按原有依赖环 / 极小冲突核心 / 时长不足逻辑归因。
- **备选节目单（k-best）**：请求 `alternatives = K`（2 或 3）时不替换原有单解 DP，而是另跑一遍 **k-best 子集 DP**：每个 `(已排/入选集合, 末尾场景)` 状态保留至多 K 条互不相同的最优路径（路径以完整下标数组保存），转移时同样逐段校验依赖、固定序位、禁止相邻与单段上限；状态桶只在作为前驱被读取前剪枝排序，因此按状态保留 K 条不会漏解。经典模式在终态上按"代价升序 → 路径字典序"取前 K 条完整排列；时长受限模式在全部含必演、不超时的路径（可来自不同入选子集）上按"价值降序 → 代价升序 → 路径字典序"在线维护前 K 条，空节目单作为无必演时的第 1 条保底解。路径字典序即按场景录入顺序（第一个分歧位次取下标更小者），保证结果确定。n=12、K=3 时复杂度约 `O(K·2^n·n²)`，实测仍在数百毫秒内。无解、必演超时、上限过低诊断等路径与单解模式完全共用。
- **演出中重排**：先逐条校验已完成前缀（跨前缀依赖按事实、固定序位按绝对位次、前缀内禁邻、前缀时长），随后在**仅含剩余场景的子问题**上运行同款 DP：
  - 固定序位换算为"前缀长度 + 后缀内位置"的绝对位次；跨前缀依赖一侧（`before` 已完成）天然满足、一侧（`after` 已完成而 `before` 未演）已在前缀校验拦截；与前缀末场景的**边界禁止相邻**作为首场景的额外可行性条件；
  - DP 初值不再是开场布置，而是 `|当前实际道具 △ 首场景道具|`，单段上限对该首段及后缀内部每次换景生效（已完成前缀不再校验）；前缀自身的代价 / 时长 / 价值按实际顺序单独累加后与后缀结果合并；
  - 被固定到前缀位次的**可选**场景在时长受限模式下自动不可入选（必演则报前缀冲突）；
  - 复杂度仍为 `O(2^r · r²)`（r 为剩余场景数，r ≤ 12）。
- **巡演装箱**：道具件数 n ≤ 14，子集 DP。先对全部 `2^n` 个子集按最低位递推出"可行箱"（总重 ≤ 承重且内部无互斥对），再求 `dp[mask]` = 恰好覆盖 `mask` 的最少箱数（`1 + min dp[mask \ s]`，`s` 取遍 `mask` 的非空可行子集），复杂度 `O(3^n)`（n=14 约 480 万次转移，数十毫秒内完成）。由于每件道具单独一箱恒可行（单件超重已在校验阶段拦截），合法配置下必然存在完整分箱。重构时逐箱取出：每箱必含当前剩余道具中录入顺序最早的一件，在保持总箱数最少的候选中优先取件数最多者、再按箱内录入顺序字典序取最小者，因此结果确定；箱内道具与箱间顺序均按录入顺序稳定展示。
- **巡演备货**：缺件 n ≤ 14，按采购包（≤ 30 个）做 0/1 背包式覆盖集 DP。`dp[mask]` 记录覆盖到缺件集合 `mask` 时的最优采购状态 `{ cost, count, packMask }`，按录入顺序逐包转移 `dp[mask ∪ cover_i] = dp[mask] + { price_i, 1 包, 包 i }`，复杂度 `O(包数 · 2^n)`（30 × 16384 约 49 万次，毫秒级完成）。状态间比较按 **总价升序 → 包数升序 → 包下标集合字典序**（两个下标集合的最低不同位上，含该位者为小，即尽量选录入更早的包），该比较在同状态扩展同一候选包时保持优劣次序，因此逐包只保留一个最优状态不会漏解，结果确定。缺件为 0 时直接返回空组合、总价 0；任一件缺件不出现在任何采购包中则判定无法覆盖并明确指出是哪几件。`npm run fuzz:stock` 用枚举全部包子集（≤14 个包）的暴力最优解对拍价格、包数与同分选择。
- **换景人员排班**：每个阶段（某段的全部撤下，或全部摆上）是一个同速平行机调度问题 `P_m‖Cmax`——m 名人员并行搬运若干件互不相干、各需正整数分钟的道具，每人一次一件，求最短完工时间。其判定问题等价于一维装箱：容量 T 的箱子能否用至多 m 个装下全部任务。用 `O(n·2ⁿ)` 的装箱 DP 做可行性判定（`dp[mask]` 为装下该集合的最少箱数，并记最后一箱已用容量，按"(箱数, 已用) 字典序"占优），再在 `[max(最大工时, ⌈总工时/m⌉), 总工时]` 上二分最短完工时间；n ≤ 14 时一次判定约 23 万次转移，毫秒级完成（实测 14 件 4 人 < 40ms）。重构出的分箱按"箱内任务按录入顺序、箱间按箱内最早任务"稳定映射到 1～m 号人员，各人任务首尾相接即给出可执行分工。段内撤下与摆上串行（摆上阶段起点 = 撤下完工时间），各段按节目单顺序串行，各段最优之和即全场搬运最短总耗时（段间无共享资源，逐段最优 ⇒ 全局最优）。

## API 简介

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/solve` | 求解，body 为 `{ mode?, timeLimit?, opLimit?, alternatives?, scenes, constraints }` |
| POST | `/api/replan` | 演出中重排，body 为求解字段外加 `{ replan: { prefixIds, stageProps, originalOrder } }`（`opLimit` 只作用于后缀；`alternatives` 被忽略） |
| POST | `/api/pack` | 巡演装箱，body 为 `{ scenes, packing: { capacity, weights, pairs } }` |
| POST | `/api/stock` | 巡演备货，body 为 `{ scenes, prepared?, packages? }`，求覆盖全部缺件的最低总价采购包组合 |
| POST | `/api/schedule` | 换景人员排班，body 为 `{ workers, durations, steps }` |
| GET | `/api/plans` | 方案列表 |
| POST | `/api/plans` | 新建方案（可带 `replanState` 持久化重排进度、`packing` 持久化装箱配置、`stocking` 持久化备货配置） |
| GET | `/api/plans/:id` | 读取方案 |
| PUT | `/api/plans/:id` | 更新方案 |
| DELETE | `/api/plans/:id` | 删除方案 |

请求中 `mode` 取 `"classic"`（默认）或 `"timed"`；`timed` 时需提供正整数 `timeLimit`（分钟）。
`opLimit` 为可选的**单段道具操作上限**（正整数，件），省略或 `null` 表示不限；求解 / 重排成功响应会原样带回 `opLimit`（不限时为 `null`），且每个 `steps` 条目的 `count` 即该段撤下 + 上台合计。
`alternatives` 为可选的备选节目单条数，取整数 `1`–`3`；省略或为 `1` 时**完全保持原有单条响应**（不出现 `alternatives` 字段）。为 `2` 或 `3` 时，成功响应在原有顶层字段（始终描述第 1 条、即最优方案）之外额外带：

```json
{
  "ok": true,
  "order": ["C", "A"],
  "totalCost": 3,
  "alternatives": [
    { "rank": 1, "order": ["C", "A"], "totalCost": 3, "opLimit": null, "steps": [ /* ... */ ] },
    { "rank": 2, "order": ["A", "C"], "totalCost": 5, "opLimit": null, "steps": [ /* ... */ ] }
  ]
}
```

`timed` 模式下每个备选条目另带 `totalValue` / `usedDuration` / `remainingDuration` /
`timeLimit` / `selectedIds` / `excludedIds`（与顶层 timed 成功响应同构）。各条 `rank` 从 1 起、
顺序两两不同；可行编排不足请求条数时返回实际条数（最少 1 条），无解时响应不变（仍为
`{ ok:false, conflict }`）。`alternatives` 非法（非 1–3 的整数）时返回 400。
经典模式场景形如 `{ id, name, props: [] }`；时长受限模式场景形如
`{ id, name, props: [], duration, required, value }`。约束形如
`{ dependencies: [{before, after}], fixedPositions: [{sceneId, position}], forbiddenAdjacencies: [{a, b}] }`。

`/api/replan` 的 `replan` 字段：

- `prefixIds`：已完成连续前缀的场景 id（按实际演出顺序，不可改变）；
- `stageProps`：当前舞台上的实际道具字符串数组（首个剩余场景代价从此计算）；
- `originalOrder`：重排前所依据的节目单，用于返回原计划 / 新后缀的对比与代价增减。重排成功响应在原求解字段之外额外包含：

```json
{
  "ok": true,
  "replanned": true,
  "order": ["C", "A"],
  "originalOrder": ["A", "C"],
  "prefixIds": ["C"],
  "suffixIds": ["A"],
  "stageProps": ["灯"],
  "prefixCost": 1,
  "suffixCost": 3,
  "originalTailCost": 2,
  "originalTotalCost": 3,
  "costDelta": 1,
  "droppedScenes": [],
  "addedScenes": []
}
```

`timed` 模式还包含 `prefixDuration` / `suffixDuration` / `timeBudget`、`prefixValue` / `suffixValue`、
`originalTotalValue` / `valueDelta`；步骤中前缀步骤带 `"phase":"done"`，首个后缀步骤带
`"phase":"suffix","fromStage":true`。前缀冲突时返回
`{ ok:false, conflict:{ type:"prefix-conflict", conflicts:[{ type, message, data }] } }`，
前缀超时为 `type:"prefix-overtime"`，剩余必演放不下剩余时长时为 `type:"required-overtime"`。

`/api/pack` 巡演装箱：请求体为

```json
{
  "scenes": [{ "id": "s1", "name": "序幕", "props": ["灯笼", "地毯"] }],
  "packing": {
    "capacity": 10,
    "weights": { "灯笼": 6, "地毯": 5 },
    "pairs": [{ "a": "地毯", "b": "王座" }]
  }
}
```

- 待运输道具由 `scenes` 中全部道具汇总去重生成（顺序：先场景序、后场景内顺序），件数不得超过 14；
- `capacity` 为正整数单箱承重；`weights` 必须为每件待运输道具给出正整数重量；
- `pairs` 为不能同箱的道具对（可选，自动去重，双方都必须已录入且不相同）。

成功响应：

```json
{
  "ok": true,
  "capacity": 10,
  "items": [{ "name": "灯笼", "weight": 6 }],
  "bins": [{ "items": ["灯笼"], "weight": 6 }],
  "totalBins": 3,
  "totalWeight": 16
}
```

`bins` 中每箱带 `items`（箱内按道具录入顺序）与 `weight`，箱间也按每箱最早道具的录入顺序排列。
单件超重（重量 > 承重）、道具超过 14 件、承重 / 重量非正整数、互斥对无效等情况返回 400：
`{ ok:false, errors:["…具体提示…"] }`。

`/api/stock` 巡演备货：请求体为

```json
{
  "scenes": [{ "id": "s1", "name": "序幕", "props": ["灯笼", "地毯", "王座"] }],
  "prepared": ["王座"],
  "packages": [
    { "name": "灯具包", "price": 8, "props": ["灯笼", "王座"] },
    { "name": "装饰包", "price": 5, "props": ["地毯"] },
    { "name": "全套", "price": 20, "props": ["灯笼", "地毯", "王座"] }
  ]
}
```

- 需求道具由 `scenes` 中全部道具**汇总去重**生成（与装箱同一口径：先场景序、后场景内顺序）；
- `prepared`：可选的**已备齐道具**数组（自动去空白 / 去重，且必须都在需求清单内）；缺件 = 需求清单 − 已备齐，种类不得超过 **14**；
- `packages`：至多 **30** 个采购包，每包 `{ name, price, props }`——`name` 非空且互不重复，`price` 为正整数，`props` 为非空道具数组且**全部来自需求清单**（包内重复道具按一件计；允许重复覆盖缺件、允许只含已备齐道具）；每个包至多购买一次。

成功响应（上例缺件为灯笼、地毯，最优为灯具包 + 装饰包共 13；下方为字段示例）：

```json
{
  "ok": true,
  "required": ["灯笼", "地毯", "王座"],
  "prepared": ["王座"],
  "missing": ["灯笼", "地毯"],
  "packages": [
    { "name": "灯具包", "price": 8, "props": ["灯笼", "王座"], "coversMissing": ["灯笼"] },
    { "name": "装饰包", "price": 5, "props": ["地毯"], "coversMissing": ["地毯"] },
    { "name": "全套", "price": 20, "props": ["灯笼", "地毯", "王座"], "coversMissing": ["灯笼", "地毯"] }
  ],
  "selected": [
    { "index": 1, "name": "灯具包", "price": 8, "props": ["灯笼", "王座"], "coversMissing": ["灯笼"] },
    { "index": 2, "name": "装饰包", "price": 5, "props": ["地毯"], "coversMissing": ["地毯"] }
  ],
  "packageCount": 2,
  "totalPrice": 13
}
```

- 选择规则：**总价最低 → 包数最少 → 按录入顺序稳定选取**（同分取下标集合字典序最小者）；`selected` 按包的录入顺序排列，每项带录入序号 `index` 与该包覆盖到的缺件 `coversMissing`；
- **没有缺件**时返回 `"selected": []`、`"packageCount": 0`、`"totalPrice": 0`；
- 缺件超过 14 种、采购包超过 30 个、包名为空 / 重复、价格非正整数、包为空或含需求清单之外的道具，返回 400：`{ ok:false, errors:["…具体提示…"] }`；
- 缺件**无法被任何采购包覆盖**时同样返回 400，错误信息列出无法覆盖的具体道具：
  `{ ok:false, errors:["以下缺件没有任何采购包包含，无法备齐：地毯"] }`，响应中不输出 `selected` 采购方案。

调用示例（curl）：

```bash
curl -X POST http://localhost:3000/api/stock \
  -H 'Content-Type: application/json' \
  -d '{
    "scenes": [{"id":"s1","name":"序幕","props":["灯笼","地毯"]}],
    "prepared": [],
    "packages": [
      {"name":"灯具包","price":8,"props":["灯笼"]},
      {"name":"装饰包","price":5,"props":["地毯"]}
    ]
  }'
```

保存方案时可在 `/api/plans` 请求体中附带 `"stocking": { "prepared": ["王座"], "packages": [{ "name": "全套", "price": 20, "props": ["灯笼","地毯","王座"] }] }`，
随方案一起持久化（仅保存输入，不保存旧计算结果；载入后需重新计算）。

`/api/schedule` 换景人员排班：请求体为

```json
{
  "workers": ["阿强", "阿芳", "阿伟"],
  "durations": { "灯笼": 6, "地毯": 5 },
  "steps": [
    { "type": "setup", "scene": "s1", "removed": [], "added": ["灯笼"] },
    { "type": "transition", "phase": "suffix", "from": "s1", "to": "s2",
      "removed": ["灯笼"], "added": ["地毯"] }
  ]
}
```

- `workers`：2～4 个非空、互不重复的人员姓名；
- `durations`：每件待搬运道具单次搬运所需的**正整数分钟**（撤下 / 摆上同值），多填节目单步骤之外的道具会报错（已完成前缀步骤中的道具允许携带但不参与排班）；
- `steps`：直接透传求解 / 重排响应中的 `steps`（可只传待执行段）；服务端自动跳过 `phase:"done"` 的已完成前缀，只对其余开场与换景步骤排班；
- 每个阶段（某段的撤下或摆上；撤下与摆上分别计数）任务数不得超过 **14**。

成功响应（各段串行；段内 `remove` 完工后 `add` 才开始）：

```json
{
  "ok": true,
  "workers": ["阿强", "阿芳", "阿伟"],
  "workerCount": 3,
  "totalDuration": 13,
  "segments": [{
    "index": 1,
    "type": "transition",
    "from": "s1", "to": "s2", "fromStage": false,
    "taskCount": 2,
    "remove": {
      "taskCount": 1, "makespan": 6,
      "assignments": [{ "prop": "灯笼", "minutes": 6, "worker": "阿强", "workerIndex": 0, "start": 0, "end": 6 }]
    },
    "add": {
      "taskCount": 1, "makespan": 5,
      "assignments": [{ "prop": "地毯", "minutes": 5, "worker": "阿强", "workerIndex": 0, "start": 0, "end": 5 }]
    },
    "duration": 11, "start": 2, "end": 13
  }]
}
```

`assignments` 中 `start` / `end` 以**本阶段起点为 0**（同一人员的任务首尾相接、互不重叠），
段的 `start` / `end` 给出该段在全场搬运时间轴上的绝对位置（摆上阶段的绝对起点 =
段起点 + 撤下 `makespan`）。人员为 2～4 名、缺少 / 非法工时、任一阶段超过 14 项任务、
没有待执行步骤等情况返回 400：`{ ok:false, errors:["…具体提示…"] }`。

`timed` 模式成功响应示例字段：

```json
{
  "ok": true,
  "mode": "timed",
  "order": ["C", "A"],
  "selectedIds": ["C", "A"],
  "excludedIds": ["B"],
  "totalCost": 3,
  "totalValue": 8,
  "usedDuration": 20,
  "remainingDuration": 0,
  "timeLimit": 20,
  "steps": [ /* 开场布置与每次换景的撤下/上台明细 */ ]
}
```

无解时返回 `{ ok:false, conflict }`；必演超时时额外带 `"reason":"required-overtime"`，
`conflict.type` 为 `required-overtime` / `dependency-cycle` / `constraint-set` / `timed-infeasible` /
`prop-limit-infeasible` 之一。`prop-limit-infeasible` 表示在既有约束下本有可行编排、但单段上限过低，
冲突对象形如：

```json
{
  "type": "prop-limit-infeasible",
  "message": "单段道具操作上限 2 件过低：……将上限放宽到 3 件即可恢复有解……",
  "opLimit": 2,
  "minRequiredLimit": 3,
  "constraints": []
}
```
